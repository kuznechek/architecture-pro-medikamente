# Задание 2 Проектирование решения

| Проблема в текущем состоянии (As‑Is) | Как решается в новой архитектуре |
|--------------------------------------|----------------------------------|
| Все данные в Excel и сканах на общем диске, доступ без разграничений | Централизованная PostgreSQL с шифрованием PII и ролевым доступом |
| Администратор, врач, бухгалтер видят одни и те же файлы, риск утечек | Keycloak + RBAC + бэкенд с обфускацией ответов по роли |
| Нет аудита — невозможно узнать, кто смотрел медкарту | Триггеры в PostgreSQL + логи Kafka + отдельное хранилище аудита |
| Ручной ввод одних и тех же данных в 1С и Excel , ошибки, расхождения | Единый источник истины – PostgreSQL С 1С обмениваются только итоги |
| Аналитика строится по файлам, нет обезличивания , нарушение ФЗ‑152 | Потоковая анонимизация (Debezium , Kafka , Presidio , ClickHouse) |
| При росте данных файловая «шара» перестанет работать | Kafka + ClickHouse – горизонтально масштабируемые системы |
| Нет автоматической выгрузки изменений в аналитику - устаревают отчёты | Debezium читает WAL PostgreSQL в реальном времени |

## Блоки новой архитектуры (добавленные по сравнению с As‑Is)

| Блок | Тип | Назначение | Почему добавлен |
|------|-----|------------|----------------|
| **PostgreSQL** | Оперативная БД | Хранит пациентов, записи, медкарты (ссылки), согласия, аудит Все PII шифруются через pgcrypto | Замена Excel и сканов: единое транзакционное хранилище с контролем доступа |
| **Debezium** | CDC-коннектор | Отслеживает изменения в PostgreSQL через WAL и отправляет их в Kafka | Позволяет передавать изменения в реальном времени без нагрузки на БД |
| **Kafka** | Брокер сообщений | Маршрутизирует события изменений по топикам (пациенты, записи, анализы, оплаты) | Асинхронная, масштабируемая шина данных, необходимая для потоковой анонимизации и доставки до ClickHouse |
| **Presidio** | Сервис анонимизации | Читает из Kafka, автоматически удаляет прямые идентификаторы (ФИО, СНИЛС, адрес, телефон), заменяет псевдонимами | Обеспечивает обезличивание до попадания в аналитику – ключевое требование Privacy by Design и ФЗ‑152 |
| **ClickHouse** | Колоночная БД (аналитика) | Хранит только обезличенные данные и агрегаты Быстрые аналитические запросы | Справляется сростом объёмов данных |
| **Airflow** | Оркестратор ETL | Управляет сложными выгрузками отчётов (ежемесячные сводки, интеграция с 1С, рассылки BI) | Обеспечивает надёжность, мониторинг и повторяемость задач по сравнению с ручным запуском или простым cron |
| **MinIO** | Объектное хранилище | Хранит сканы медкарт, снимки, PDF с шифрованием на стороне сервера (SSE‑S3) | Убирает файловую «шару», добавляет контроль доступа и шифрование для документов |
| **Keycloak** | IAM / SSO | Управляет пользователями, ролями, выдаёт JWT токены, поддерживает 2FA | Решает проблему аутентификации и разграничения доступа (администратор, врач, бухгалтер, пациент) |
| **Единый бэкенд-сервис** | API-сервер (BFF + Privacy Gateway) | Принимает запросы, проверяет JWT и права, обфусцирует ответы по роли, логирует доступ, работает с PostgreSQL и MinIO | Заменяет ручные действия в Excel, единая точка входа упрощает контроль и внедрение политик безопасности |

## Соответствие принципам Privacy by Design

| Принцип | Реализация |
|---------|-------------|
| **Privacy by Default** | Все PII шифруются в PostgreSQL (pgcrypto, AES-256) |
| **Data Minimization** | В ClickHouse попадают только обезличенные данные |
| **Data Lineage** | Логи всех изменений есть в Kafka и в таблице аудита PostgreSQL |
| **Access Control** | Keycloak + RBAC Бэкенд проверяет роли и применяет обфускацию на лету |
| **Consent Management** | Таблица `consents` в PostgreSQL проверяется при каждом обращении к PII пациента |
